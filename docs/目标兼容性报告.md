## 用户指定的 SDK 路线

用户先允许 ImmortalWrt 21.02，随后允许尝试 24.10。保留两条候选，不因更换 SDK 改写设备固件信息、Lua/IPK 基线或声称 ABI 通过。清单只记录候选 URL 和官方公布 SHA；正式 sdk.url/sha256 仍为空，待完整兼容证据后固定。

| 候选 | 官方可见内容 | 本项目状态 |
|---|---|---|
| ImmortalWrt 24.10.6 qualcommax/ipq807x | SDK 文件使用 GCC 13.3.0/musl；官方目录提供 SHA256 | 用户允许的候选，同 SoC 家族但跨固件分支；未下载/编译/实机加载 |
| ImmortalWrt 21.02.7 mediatek/mt7622 | SDK 文件使用 GCC 8.4.0/musl；官方目录提供 SHA256 | 用户态交叉编译备选；不同 SoC，架构及运行库兼容仍须验证 |

2026-10-11 查阅的官方 21.02.7、21.02-SNAPSHOT targets 索引未列 ipq807x。该观察不等于整个 21.02 生态绝无可用工具链，也不证明 mt7622 SDK 一定兼容。21.02.7 的 aarch64_cortex-a53 通用包目录存在，只能说明有对应包仓库，不能替代 SDK ABI 验证。

24.10.6 的 SDK 与 SHA 已登记，优先可作编译原型候选。任何复用都先比较 ELF interpreter、libc、动态库 SONAME/符号、目标 CPU 指令集与依赖元数据。Shell/纯 Lua 文件也要验证目标命令选项与 LuCI API；并不能因为没有本插件 ELF 就免测外部组件。仅使用用户态产物，不从异版 SDK 为当前固件安装内核模块或批量替换系统基础库。

补充报告表明有明确的跨分支差异：QWRT 使用 libubox20191228、libubus20210603、libjson-c2 与 OpenSSL 1.1 系列。2026-10-11 查阅的 ImmortalWrt openwrt-24.10 当前配方使用 OpenSSL 3 和日期为 2024-03-29 的 libubox ABI。这是分支源码比较，**不是已下载 24.10.6 SDK 的库检查**；正式决定仍须固定 SDK/feeds 并检查实际 ELF。直接链接 24.10 默认系统库的 C 包不能据此标为可在当前 QWRT 安装。Shell 原型可先调用目标已有命令，C 若采用则须匹配旧库或经验证的私有依赖方案。

目标清单同时保留包元数据和实际命令输出：`libopenssl3 - 1.1.1w-1` 不能证明系统提供 OpenSSL 3 ABI；实际 openssl/curl 均报告 1.1.1x。curl 构建 triplet 中出现 linux-gnu 也不覆盖 musl loader 证据。暂不猜测别名或厂商补丁来源。
